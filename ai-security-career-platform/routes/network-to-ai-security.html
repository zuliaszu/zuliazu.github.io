Free learning route

From network security to AI security

Apply your network-security skills to an AI assistant. Map its connections, restrict what its tools can do and plan tests that show whether those controls work. Use one fictional firewall-change assistant throughout.

For: Network engineers and network-security professionals moving into AI security, including those working mainly on premises.

Before you start: Basic familiarity with firewall rules, DNS and TLS. No coding or cloud experience required. The first lesson explains the AI terms; the AI fundamentals route offers more background.

First task: about 20 minutes. Then four lessons of about 20 minutes each. The first session is a starting point. Lesson estimates total about 80 minutes, plus the first task, final write-up and optional courses.

Practise in this route

  • Draw the connections and access boundaries of a tool-using AI application.
  • Choose network controls and explain which risks need application or identity controls.
  • Restrict a tool to the data and actions its task needs.
  • Write allowed and denied test cases with the evidence needed to check each result.

Start now · about 20 minutes

Map a fictional firewall-change assistant

  1. Imagine an assistant running locally on a network engineer's workstation at the fictional Calder Networks. It reads invented runbooks from an internal document service and sends selected text to a hosted language model. It can create draft tickets in an internal ticketing service, but cannot approve changes or modify a firewall.
  2. The assistant also starts a local file-reading tool. This tool may read only a folder of invented configuration files and needs no network access. Use fictional data throughout; do not copy work configurations or credentials.
  3. Draw six components: engineer, local assistant application, hosted model endpoint, internal runbook service, ticketing service and local file tool. Connect the engineer to the application. Connect the application separately to each service and to the local tool.
  4. Mark the application-to-service connections as network traffic. Mark the application-to-local-tool connection as local process communication. The model returns proposed tool calls; the application checks and executes them.
  5. Beside each connection, write both what may connect and what the caller may do. Limit runbook reading to documents the engineer may access. Limit tickets to drafts in one project. Limit local file reads to the exercise folder.
  6. Name one way data could reach the wrong audience even if all network connections were allowed and encrypted.

Done when: You have a labelled diagram, a permitted action for each service or tool, and one risk that network controls alone cannot prevent.

Check the first task

The local application calls the hosted model, runbook service and ticketing service over separate authenticated connections. Network policy restricts their destinations. The model does not connect directly to the internal services in this design. The application checks the engineer's access before reading each runbook and limits its ticket credential to draft creation in one project. The local file tool communicates through process input and output; file permissions or a sandbox restrict its readable folder. Its own outbound network access is denied. A draft ticket could still reveal runbook text to people who cannot read the original. Restrict source data and ticket visibility before creating the draft. A human may also approve a plausible but incorrect recommendation. This paper design describes intended controls; it does not prove they work.

Lesson 1 · about 20 minutes

Map the AI system

A large language model generates responses from the input it receives. A model endpoint is the interface an application calls to use it. An API is a programmatic interface; the model API in this exercise uses the network.

Retrieval supplies documents to the model alongside a question. Retrieval-augmented generation, or RAG, uses this retrieved content to help produce an answer. The application must first check which documents the requesting engineer may read. A read-only service credential alone does not enforce each user's access.

A tool call is a structured request from the model, such as create_draft_ticket with a title and description. In this design, the application validates and authorises that request before executing it. Draw service connections from the application, not from the model. Other deployments may use provider-hosted tools; map the actual execution location when reviewing those.

Network controls limit connections. Authorisation controls decide which caller may perform which action on which resource. Authentication establishes the caller's identity. NIST's zero trust guidance says network location alone should not establish trust. Mark pasted notes and retrieved documents as untrusted instructions, even when they came through an approved connection.

Try it

Add a credential or identity to each service connection on your diagram. Write the narrowest permitted action beside it. Mark each flow carrying pasted notes, retrieved text or tool output.

Check your answer

The model credential permits the required model calls. Runbook access is read-only and filtered to the requesting engineer's permitted documents. The ticket credential creates drafts in one project without approving changes. The local tool reads only the exercise folder. Notes, retrieved content and tool results may contain unwanted instructions. Model output also needs validation before use. Record missing access-policy details as questions rather than assuming they exist.

Lesson 2 · about 20 minutes

Secure the connections

Segmentation separates network zones and restricts traffic between them. Give the assistant access to the services it needs, rather than the entire internal network. Egress means outbound traffic. Restrict it to approved destinations, with an explicit purpose for each connection.

A private endpoint provides a private network path to a supported service. It does not grant permission to use that service. Check routing and DNS, the system that resolves service names to addresses, from the client's actual location. An on-premises client may need additional private connectivity. A private endpoint existing somewhere in a cloud account does not prove the client uses it.

TLS protects data in transit when configured correctly. Keep certificate and hostname verification enabled so the client can authenticate the server it intended to reach. This does not establish whether the request is authorised or what the recipient retains. Check those separately.

Server-side request forgery, or SSRF, occurs when an attacker abuses an application to make unintended requests. A browsing tool might receive an attacker-influenced URL from a document. Our assistant needs no browsing tool, so leave it out. If one is later required, restrict destinations in code and network policy. Validate resolved IPv4 and IPv6 addresses, prevent unsafe redirects and block unintended internal or metadata-service access. Enforce checks on the destination actually contacted; DNS changes must not bypass them.

Try it

Write a connection table with source, destination, purpose and control columns. Include the model, runbook and ticketing services. Decide whether a generic URL-fetching tool is needed. Explain how you would verify a proposed private connection.

Check your answer

Permit the local application to reach the approved model endpoint and the two internal services. Use endpoint or network policy for reachability, TLS validation for transport protection, and separate service permissions for actions. Do not add generic URL fetching without a requirement. Verify DNS resolution and routing from the workstation before claiming traffic takes a private path. If private connectivity is unavailable, assess an approved TLS-protected public path rather than assuming the service is automatically unsafe. Provider retention and data-use terms need a separate review.

Lesson 3 · about 20 minutes

Limit what permitted traffic can do

Prompt injection is an attempt to make a model follow instructions embedded in untrusted input. Direct injection comes through a user prompt; indirect injection arrives through material such as a retrieved runbook. Design for the possibility that the model requests an unwanted action. A prompt telling it to behave is not an enforceable permission boundary.

Excessive agency means an AI system has more functionality, permissions or autonomy than it needs. Give this assistant draft creation only. Keep firewall administration and ticket approval outside its tools and credentials. The application and downstream service must enforce these limits regardless of the model's request.

An allowed destination can still receive inappropriate data. A draft ticket may be visible to more people than the source runbook. A domain allowlist limits destinations; it cannot by itself decide which information or recipients are appropriate. Data loss prevention, or DLP, adds checks on sensitive information and its movement. Content scanning can miss information, so also restrict retrieval and output audiences.

Limit the ticket project, allowed fields and actions. Apply size and rate limits, and check destination visibility before storing sensitive content. Schema validation checks structure, not whether text is safe or authorised to disclose. Human approval should show the exact proposed change. Our assistant never applies it; a separate authorised change process handles execution.

Try it

Explain why approving the ticketing API does not approve every possible ticket body. Write restrictions for the project, actions and data. Name one risk that remains.

Check your answer

Allow draft creation only in the designated project. Deny approval, firewall changes and other ticket operations. Retrieve only documents the engineer may access and whose information may reach the draft's audience. Validate fields and apply size and rate limits. A short, valid ticket can still contain sensitive information or a wrong recommendation. Review the actual content and its audience before saving or sharing it; a later approval step cannot undo an earlier disclosure.

Lesson 4 · about 20 minutes

Test and monitor the controls

Write tests for actions that must succeed and actions that must fail. In this route, describe expected results on paper; do not scan or change a real system. For a future authorised lab, record actual results separately. Repeated model tests reveal observed behaviour, while policy and code tests check enforcement boundaries.

Network logs show connections and destinations. Application and service audit logs show requested actions, policy decisions and resulting changes. Use application request identifiers where supported. Network flow logs often lack these identifiers; correlate them using timestamps, workload identity and connection details. Distinguish a proposed tool call from an executed action.

Model Context Protocol, or MCP, is one way applications connect to tools. Its stdio transport exchanges messages through a local process's standard input and output. That communication does not cross a remote MCP gateway. Host permissions or sandboxing must restrict file access and credentials. The tool process can still make outbound network connections, which host or network policy can restrict.

HTTP-based MCP servers use network connections. For a local HTTP server, loopback binding limits exposure; Origin validation helps defend against browser-origin attacks such as DNS rebinding. These controls do not replace authentication and authorisation. They do not apply to stdio communication, which has no HTTP headers or listening socket. Check the protocol revision your implementation uses.

Log only what investigations need. Protect access and set retention limits; do not routinely record credentials or entire sensitive prompts. For this exercise, use fictional record identifiers and policy decisions. Retest after changes to tools, permissions, models or retrieved content. Record remaining risks and missing evidence.

Try it

Write three allowed cases and three denied cases. Include the local file tool and its outbound access. For each case, name the enforcing control and the evidence you would expect. These are expected outcomes, not tests you have executed.

Check your answer

Allowed: a model request through the approved path, a read of a runbook the engineer may access, and a draft in the designated project. Check transport records and the relevant service audit events. Denied: creating a ticket in another project, reading a local file outside the exercise folder, and the local file tool contacting an external service. Expect a downstream permission rejection, a file-access denial, and a host or network deny event respectively. A firewall log cannot prove which local file was read. Check application records for proposed versus executed calls, and record any evidence gap. For a future URL-fetching tool, add internal-address, metadata and redirect test cases.

Keep what you made

A security review of your fictional assistant

Keep your diagram, connection table and tool-permission notes together with your expected test results. Label this as a paper design exercise. It becomes implementation evidence only after you build and test an authorised system.

  • The diagram places network calls at the component that executes them.
  • Each service has both a connectivity restriction and a permitted action.
  • Document access accounts for the requesting engineer and the destination audience.
  • The assistant can draft tickets but cannot approve or apply firewall changes.
  • Local file restrictions and the tool process's own egress are covered.
  • Each test names its expected outcome and evidence; no test is presented as executed.
